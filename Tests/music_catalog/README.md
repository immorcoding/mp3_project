# 音乐曲库主机测试

第一个测试程序 `music_catalog_name_tests` 通过 `catalog_name.h` 验证曲目显示名纯函数：取最后一个 `/` 之后的部分，只去掉末尾 `.mp3`（`m`、`p` 两位大小写任意，与曲库扫描 `catalog_music_file_strcheck` 接受的形式一致），其余原样保留；只有扩展名的文件（如 `.mp3`）保留整名；主名超过 251 B 或不是合法 UTF-8 时失败，不截断、不写半个字符，失败时输出缓冲为空串。只编译 `catalog_name.c`，不链接 FreeRTOS、FatFs、HAL 或曲库字符串池。

第二个测试程序 `music_catalog_text_tests` 通过 `catalog_text.h` 验证曲目文本纯函数，也是 `Components/id3_reader` 的唯一测试接缝（不单开模块）。它用字节数组构造假文件，经“按偏移读”回调提供，并链接真实 `cc936.c`（复制 `FATFS/Target/ffconf.h` 并去掉 MCU 头）实现 GBK 查表。覆盖：v2.2 / v2.3 UTF-16LE / v2.4 UTF-8；真 Latin-1、声明 Latin-1 实为 GBK、结构合法但无映射的码位回退 Latin-1；缺 BOM、BE BOM、多值各自 BOM、代理对；多值连写、`AC/DC`、首尾空白与 U+3000、全空白回退、NUL 填充；超长按字符边界截断与截断后仍校验；非法 UTF-8 / 孤立代理 / 奇数长度 / 编码字节 > 3 / 控制字符 / 压缩或加密帧；v2.4 帧级去同步、数据长度指示、分组字节，扩展头；帧顺序不固定与重复帧；无标签、帧缺失、非法帧 ID、帧越过标签末尾、标签头不可读；首块读取偏移与长度、APIC 前置跨首块 seek 且不越过标签总长、帧负载跨块边界、恰 4 次读取与超读取上限、读取错误注入、首块读入的标签之后字节（形似 TIT2/TPE1 帧）不被解析、标签级去同步 v2.3（含超出首块）、TIT2 可用而 TPE1 坏、文件主名提取失败的防御分支。

曲目文本程序不再含编译期断言：单行预算 `CATALOG_TRACK_BUDGET_US` 现在只是 1 s 的日志阈值，不再等于 T_data/2，也就不再把播放任务的配置头拉进本模块（改 `playback_task_config.h` 不选中本模块）；它大于另外两个预算的两条断言留在第三个程序里。

第三个测试程序 `music_catalog_open_tests`（`test_catalog_open.c`，STOR-1、STOR-7、STOR-17、ARC-19、ARC-22、DIAG-4、DIAG-5、DIAG-6，#179、#212、#220）链接真实 `catalog.c`、`catalog_sheet.c`、`catalog_track_open.c`、`catalog_track_text.c`、`catalog_track_diag.c` 与曲目文本纯函数，只把 Filesystem Service 公开函数（目录扫描、`OpenFile`、`OpenFileByLocator`、读/seek/关闭）、Log Service、周期计数器 Adapter 与卷状态函数 `volume_status()` 换成测试文件里的假实现，曲库短锁走共用 FreeRTOS 桩；**扫描经单步函数 `catalog_scan_step()` 驱动**（测试文件的 `step_once()` 对每一步断言“目录调用不超过一次”，把返回的等待毫秒数推进假时间，`run_to_idle()` 跑到它要求等通知为止）（`Tests/stubs/freertos`）（合成曲库，定位符由文件 id 派生；假 DWT 为 1 MHz，周期即微秒）。覆盖：曲库上限 12000 的编译期与运行期核对（12500 条目扫描后恰收录 12000 条、末条定位符完好、超出截断仍成功并记一次 `Music Catalog Full.`）、池大小与每首可用路径空间、新阈值常量（单行打开 30 ms、整窗 0.5 s）均小于 1 s 的单行日志阈值（两条小于断言）；扫描时每条（含子文件夹内）随附正确的定位符，定位符只在同一曲库代次内可取；按曲库下标读曲目文本走定位符而不走路径，打开耗时单独给出；核对不符（介质已变）与扫描时没取到定位符（全零）都退回按路径打开同一首、两次尝试都计入打开耗时、记一行 `Locator miss pos=N` WARN（位置取播放列表位置而非曲库下标，每次各记一行）；其他失败（槽用尽）不退回路径、不记 miss、回退文件主名；下标越界返回空；曲名 INFO 带 `open=` 且 `us=` 不含打开；窗口汇总行在单行打开恰 30 ms、整窗恰 0.5 s 时静默，单行打开 30001 µs、整窗 500004 µs、WARN 级原因、1 s 单行日志阈值任一出现时触发，汇总行放得进 Service Log 的 128 B；`Stream pos=N off=<B> open=<us> lseek=<us>` 行格式；扫描结束 INFO `Scan done res=<ok|dfs_error|aborted> n=<条数> us=<微秒>`（#204，DIAG-6）：格式与 tag、耗时取目录读取花掉的假 DWT 时间（含计数器在扫描中途 32 位回绕）、每次重扫各一行且按本轮算、没有 `Music/` 为 `ok n=0`、12500 条截断为 `ok n=12000`、目录读取失败为 `dfs_error`；卷不可用（`NO_MEDIA`、`NOT_READY`、`INVALID_HANDLE`，#211）：打开 `Music/`、打开子目录或扫描到一半读目录得到它们时，丢弃本次扫描、不发布播放列表（曲库保持无效）、不记 ERROR、结束行写 `res=aborted n=0`，其他失败（`SERVICE_ERROR`）仍按空库发布；曲目标签读取打开时得到它们返回空结果，不回退文件主名、不退回路径打开。每个用例末检查没有泄漏的打开句柄。

新增（#212）：**发布规则**——重扫期间读者经一次读全看到代次 0、位置无效、路径为空串（上一份曲库的内容不漏出）；代次只在发布时加 1、重扫与作废都不重复、作废不拨回计数；**取代次时卷序号不符就算 0**——换卡（序号跳 2）或拔卡后没有调用作废，`catalog_generation()` 与一次读全也得 0。**卷序号**——扫描途中换卡（读目录时序号变了）关目录（关目录的返回值不看，注入失败也不影响）、丢弃、不发布、不记 ERROR，之后在新序号下重扫能发布；扫描做完发布之前换卡不发布；卷在开扫时就不在不发布。**读者一次读全**——代次、条数、路径、定位符来自同一次拷贝，子文件夹里的最后一条正确，越界位置带回代次和条数且路径为空，空指针返回假。**曲库短锁**——扫描只在开始和发布各拿放一次；读者、取代次、作废各拿放一次；假文件接口与假日志里断言“此刻曲库锁没被持有”（持锁不调文件调用、不投日志）；用桩让接下来 2 次拿取失败，读者等到拿到后数据完整、超时是无限等待。**错误表**——`SERVICE_BUSY` 在打开根目录、读目录、关目录各一处重试且不算失败（至少等 4 个 10 ms，没有 WARN/ERROR），重试等的时候卷序号变了就作废；关目录得到卷不可用的三种返回值丢弃；打开根目录的其他错误按空库发布并记 WARN；打开子目录的其他错误跳过该子目录并记 WARN、其余照常发布；读目录或关目录的其他错误不发布并记 ERROR；条目满发布截断结果。**持锁统计（Debug）**——节拍没到不投，到了在放锁之后投一行 `CATLOCK: n=<次数> hold=<微秒>us`，同一节拍内不再投，下一节拍再投；最长持有取开机以来的最大值，只量持锁区间（锁外的慢文件调用不计）；行放得进 Service Log 的 128 B。**#211 随搬家并入的用例**：打开目录得到卷不可用时再开一次（根目录与子目录各一例，第二次恢复则扫描照常完成并发布；两次都失败才丢弃，`OpenDirectory` 恰被调用 2 次）；`catalog_scan_verdict(volume_unchanged)` 三种结果（完成 / 等卷事件 / 卡还在读不了），根目录卷不可用、读目录卷不可用、子目录卷不可用三个丢弃用例都断言；**前台一次切（#218）**：槽已删除，原先的 `complete_unavailable` 用例换成三条——曲目文本读取遇到卷不可用（打开得到 `NO_MEDIA` 等）时向调用者报告“卷不可用”并且不回退文件主名、不计“打开失败”，标记被下一次读取清除；打开得到 `SERVICE_BUSY`（文件槽用尽）时标记 `OpenBusy`，调用者据此过约 10 ms 重试、不缓存；曲库发布成功叫醒前台任务恰好一次，被丢弃的扫描不叫醒（本程序另有 `foreground_task_wake()` 的假实现，计数）。槽相关的主机测试随槽一起删除。池满（`Music Catalog Pool Full.`）按 12000 条与 4 MiB 池的设计到不了，主机测试不覆盖。

**扫描单步（#220，ARC-22）**：扫描从 Storage Task 的同步调用改成后台任务里的单步作业，`catalog_music_init()`、`catalog_init()`、`catalog_scan_verdict()`、`catalog_invalidate()` 和 `Catalog_StatusTypeDef` 都没有了，原来的扫描用例改用 `scan()`（卷挂载并跑到做完；第二次起先让卷序号加 2，因为扫描只在卷序号变化后发生）和 `unmount_card()`。新增：**一步一次目录调用、一步读一条**（驱动函数对每一步断言；12 次目录调用与目录树一致）；**没有活时只等通知**（卷没挂、已发布，每一步不碰文件接口、不拿曲库锁、不投日志）；**`SERVICE_BUSY` 返回 10 ms 而不是在步里等**；**目录树遍历结果与改成单步之前一致**（嵌套、隐藏目录、非 mp3 文件、大写扩展名、空目录；期望顺序是用旧的同步实现在同一棵树上跑出来的一次性对照）；**每步比对卷序号**（扫描中途换卡关目录且返回值不看、记 `aborted`、不发布、之后从头重扫并发布、发布前换卡不发布、重试等的时候卷序号变了不再用旧序号继续）；**卡在、读不了**（卷不可用而卷序号没变：第一次失败后再开一次，仍失败则记 `aborted` 加一条 ERROR 要求重插卡，之后再跑多少步都不碰文件接口、不记日志，卷序号变化才重新开始）与**卡被拔走**（安静丢弃、不记 ERROR、等卷事件，只开一次目录就看到卷序号变了）；`Scan done` 的 `us=` 是从开始到结束的总时间，含 BUSY 的睡眠（`us=10000`）。

第四个测试程序 `music_catalog_release_tests`（`test_catalog_release.c`）：曲库源码（`catalog.c`、`catalog_sheet.c`、`catalog_name.c`）编进 OBJECT 库单独带 `-DNDEBUG`，与固件 Release 一致，测试文件与桩仍带断言。证明发布构建里读写曲库、节拍早已过去也不投 `CATLOCK` 汇总，其他日志照常，发布规则（代次递增、取代次时卷序号不符算 0）不受开关影响。

保真边界：主机测试是单线程的，通过不等于并发没问题——曲库短锁的用例（拿放次数、拿不到锁、文件调用与日志不在锁内）只证明分支走对了，不证明真实任务抢占、优先级继承、读者与扫描者真实交错时的内存可见性，也不证明持锁的真实时长（板上看 `CATLOCK` 行）；扫描单步的用例证明状态机的分支、返回值和发布结果，不证明后台任务与 Flash 启动任务同级时真实分到多少 CPU（开机扫描时长靠第 6 次上板）。PASS 只证明提取规则本身。后台任务外壳（`background_task.c`）不做主机测试，进板级验收（Queue 窗口与曲名的前台流程见 `Tests/music_foreground`）；曲库扫描证明随条目写入定位符、上限截断、错误表与发布规则，不证明真实目录扫描耗时；真实按定位符打开由 `Tests/filesystem_locator` 证明，这里的假 `OpenFileByLocator` 只复现三态约定，不证明它与 FatFs 的核对一致；开流路径（音频读取任务的 `audio_reader_stream.c`）改用同一打开入口，但该文件含信箱与 FatFs 盖章，不做主机测试，`Stream` 行只钉格式，其耗时取值与 `open`/`lseek` 的口径由板级验收（O3、O4）取证；扩展名大小写与扫描代码的一致性靠人工对照，不由测试自动保证。曲目文本函数的 PASS 只证明规则链与读取计划（偏移、次数、不越过标签）；不证明 FatFs 实际读取、`f_open` 失败判定、SD 耗时与单行时延预算，也不证明板上 CP936 表已就绪或 `Service_Filesystem_GbkToUnicode` 的接线，这些进板级验收（#135 I1–I13）。测试里的 GBK 回调直接调 `ff_convert`，与生产薄函数同源但不是它。

从仓库根目录运行：

```powershell
./scripts/test-host.ps1 -Module music_catalog
```

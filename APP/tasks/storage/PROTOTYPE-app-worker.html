应用架构 C：应用任务持锁读 SD

要回答的问题：按选项 C 分工之后，应用接入、界面、音频和拔卡分别表现如何？这些规则碰到棘手情形会不会漏？和现状写法、A（请求队列）比差在哪？

这是逻辑模拟，不是板测。各写法跑同一批操作、同一组耗时参数，每 1 ms 模拟一次 FreeRTOS 抢占、时间片和互斥锁（放锁时高优先级等待者立刻抢占，持锁者继承等待者的优先级）。部分耗时是假设，见页面底部。Books、Settings 现在还不存在，“现状写法”指继续按名称槽的方式接入它们。C 和 A 用同一份应用代码，只有文件接口的内部实现不同。

C 长什么样：谁持锁、谁能等

应用任务（上一版叫 Worker）就是一个普通的 FreeRTOS 任务，专门替应用做“需要等”的事。GUI 不能等，所以读文件、读标签都放在这里。应用代码本身看不到 SD 锁：锁在 Filesystem Service 的每个公开函数里，进门拿、出门放。

任务优先级只做什么绝不做
播放4解码、补 PCM碰文件、拿锁
音频流3读文件、填块池，到安全水位后让路解码
卷管理3消抖、挂载卸载、发布卷事件具体的文件读写
GUI2LVGL 和不用等的交互，没活就睡等文件、做重活
应用任务2前台流程（读书页、读标签）和当前曲信息CPU 重活
后台任务1扫描、建索引、解码封面、存设置抢前台

应用任务：翻一页书（示意）

void books_turn_page(int n) {
    file_t f = fs_open(SD, book_path);  /* 里面拿锁、做完就放 */
    fs_read(f, offset_of(n), buf, len); /* 等 DMA 时持 SD 锁 */
    fs_close(f);
    layout_page(buf, &page);            /* 不持任何锁 */
    book_model_publish(&page);          /* 短锁，只拷贝内存 */
}

/* GUI 任务：只取结果，永远不等 */
void gui_books_step(void) {
    if (book_model_take(&page)) show_page(&page);
}

Filesystem Service：每个公开函数都这样（示意）

status_t fs_read(file_t f, ...) {
    assert(!is_gui_or_playback_task());  /* 规则 4 */
    lock(volume_lock(f));    /* 按优先级排队，带优先级继承 */
    status_t s = read_block_unlocked(f, ...);
    unlock(volume_lock(f));  /* 绝不跨调用持有 */
    return s;
}

/* 音频流任务：到安全水位后每补一块让一下 */
fs_read(stream, block->Data, BLOCK_BYTES);
if (blocks_ready() >= LOW_WATER) vTaskDelay(1);

C 必须守住的规则：

  1. 锁藏在 Service 里：一次公开调用拿一次，返回前放掉，绝不跨调用持有。
  2. 它是最内层的锁：持有界面数据锁时，不许调用文件接口。
  3. 持锁时长有上界：一次最多读 32 KiB，扫描按批做。
  4. 调用者受限：GUI 和播放任务一调用文件接口就断言失败。
  5. 音频到水位后让路。

这个原型回答不了的问题

  • FatFs 能否每卷一把锁：要把 _USE_LFN 从 1 改成 2 或 3；文件锁表 Files[] 跨卷共享且没有保护（ff.c:541），官方文档没提。可以把 _FS_LOCK 设为 0 由 Service 自己查重（Flipper 的做法，待核实），或者先用一把全局锁。把参数“每卷一把锁”改成 0 可以看全局锁的效果。
  • 任务的栈够不够：音频流、应用任务、后台任务、卷管理都会走到 FatFs，都要留深栈，需要实测内部 RAM。
  • 完成通知：SD、Flash 的完成通知要改成不绑定任务；未决的“迟到 DMA 完成事件”要一起解决。这里没有模拟。
  • 排版能否放在 LVGL 之外：LVGL 不是线程安全的，读字体这条路径要先确认。
  • 多少算重活：这里 40 ms 的排版留在应用任务，会把帧间隔撑到约 50 ms。阈值要板测后再定。
  • 真实耗时：SD 吞吐、擦除、解码、排版都是假设值。GUI 从不睡是读代码得到的（gui_task.c:56），没有实测 CPU 占比。

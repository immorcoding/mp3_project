应用架构对比：Worker 到底解决什么

要回答的问题：把应用分成“GUI 一半 + Worker 一半”、文件操作走通用请求之后，同样的操作和现在的写法相比，界面、音频和接入成本分别怎么变？新规则碰到棘手情形会不会出问题？

这是逻辑模拟，不是板测。三种架构跑同一批操作、同一组耗时参数，每 1 ms 模拟一次 FreeRTOS 抢占和时间片，请求往返的开销按 0 计。部分耗时是假设（见页面底部的参数）。Books、Settings 现在还不存在，“现状写法”指继续按名称槽的方式接入它们。

Worker 是什么

Worker 就是一个普通的 FreeRTOS 任务，和 GUI、Storage 并列。它专门替应用做“需要等”的事。等 SD 时它睡着，不占 CPU，其他任务照常跑。

打个比方：GUI 是不能离开大厅的服务员，Storage 是唯一能进仓库的管理员，Worker 是跑腿的。跑腿的拿单子去仓库门口等货，服务员继续招呼客人，管理员也不用学会做菜。在下面的时间线里，Worker 一行的斜纹就是它在等。

现状写法：翻一页书（示意）

/* GUI 任务：不能等，只能每帧查一次状态 */
void gui_books_step(void) {
    switch (book_slot.Status) {
    case IDLE:
        if (want_page) storage_bookbuffer_request(page);
        break;
    case READY:
        layout_page(book_slot.Data);  /* 排版也卡在 GUI 里 */
        book_slot.Status = IDLE;
        break;
    }
}

/* Storage 任务：主循环多一步，还要懂“书” */
void storage_bookbuffer_load(void) {
    if (book_slot.Status != PENDING) return;
    read_book_chunk(book_slot.Page, book_slot.Data);
    book_slot.Status = READY;
}

/* 另外还要：新 FLAG、bind、拔卡收尾、主循环调用…… */

新架构：翻一页书（示意）

/* GUI 任务：只取结果，永远不等 */
void gui_books_step(void) {
    if (book_model_take(&page)) show_page(&page);
}

/* Worker 任务：可以写“读完再往下” */
void books_turn_page(int n) {
    file_t f = storage_open(book_path);   /* 发请求，睡到结果回来 */
    storage_read(f, offset_of(n), buf, len);
    storage_close(f);
    layout_page(buf, &page);              /* 重活也不卡界面 */
    book_model_publish(&page);            /* 短锁写入，GUI 下一帧看到 */
}

/* Storage 任务：不用改。
   它只执行 open / read / close，不知道“书”是什么。 */

这个原型回答不了的问题

  • Worker 和后台任务的栈放哪、够不够：需要实测内部 RAM。
  • SD 实际吞吐、封面解码和排版的真实耗时：页面上是假设值。
  • 在 Worker 里排版时读字体是否安全：LVGL 不是线程安全的，要先确认只读路径。
  • _FS_LOCK 现在是 2，新架构同时打开的文件对象更多，要调大（ffconf.h，改之前要你确认）。
  • “Worker + 拿锁直接读 SD”（上一轮的选项 C）这里没有单独模拟。

# Inbox: ticket-207-completion-signal

- 2026-11-05 · architecture · cite · ARC-11 · 已按 #207 落地（分支 `ticket-207-completion-signal`，基于 `ticket-205-gui-sleep`，未上板）：SD 与 Flash 各一个静态二值信号量，`InitSD()`/`InitFlash()` 去掉 `notify_index`，两个执行器不再绑定任务，正在执行传输的任务等待，ISR 回调只用 `xSemaphoreGiveFromISR` 并把 `higher_priority_task_woken` 交给 `portYIELD_FROM_ISR`。规则文字里“持卷锁的任务等每卷一个信号量”的前半句已成立，“持卷锁”要等 #208 加锁后才成立；这张票之后 Storage Task 仍是唯一调用者。是否升 settled 等第 2 次上板。
- 2026-11-05 · architecture · proposed · ARC-11 · 建议补一句初始化约束：`InitSD()`/`InitFlash()` 第一次调用创建信号量，必须在任何任务使用文件接口之前、单线程完成（现在是 Storage Task 启动时，#208 之后应归 Boot 或卷任务）；重复调用不重建信号量。_Why:_ 静态信号量用惰性创建，没有临界区保护，两个任务同时第一次调用会重复初始化同一块存储。代价是多一条调用顺序约定；替代做法（创建放进 `Service_Filesystem_Init` 之类的单独入口）要加公开函数，超出 spec M 节授权，没有采用。
- 2026-11-05 · architecture · proposed · ARC-11 · 建议补“迟到的旧信号”规则：完成信号量在每次启动传输之前清空——SD 在 `Platform_SD_Start*Blocks` 之前（Start 之后清会丢本次自己的中断），Flash 在 Start 之后、第一次 `Process` 之前（`Process` 才是权威）。_Why:_ 超时之后才到的完成中断会让信号量保持置位；不清，下一次等待会被旧信号“完成”。“旧 DMA 在清理之后、启动之前才完成”这个窗口清不到，仍归 #209 的显式 Abort。主机测试 `filesystem_completion_wait` 覆盖前一半；临时去掉清理，SD 与 Flash 各一个用例失败。
- 2026-11-05 · storage · cite · storage.md 未决问题（迟到的 DMA 完成事件） · 读 `Components/sd/sd.c` 确认：超时后执行器向 Platform 提交 ERROR，`SDCard_FailTransfer` 把 Device 置 `ERROR`，`SDCard_StartReadBlocks` 在 State 不是 READY 时直接拒绝（`sd.c` 第 621 行附近）。所以旧 DMA 的迟到完成与下一次成功启动之间，卡必须先被重新初始化（例如拔插之后；哪条路径会把 `ERROR` 拉回 `READY` 我没有逐条读），窗口比“超时后紧接着再读”窄得多，这也解释了 #188/#191 为什么构造不出来。这是读代码的结论，不是板测；板测仍按 R2.2 的“单块超时调到 1 ms 再读并校验内容”做，要同时看超时后第一次 `Start` 是否被拒绝。
- 2026-11-05 · storage · cite · ADR-0024 第 6 条 · “非 owner 时磁盘状态报 `STA_NOINIT` 可能触发 FatFs 重挂（推断）”现在读 `ff.c` 确认：`find_volume` 对已挂载的卷调用 `disk_status`，返回 `STA_NOINIT` 就清 `fs_type` 并走重新挂载（`ff.c` 第 3020 至 3036 行）。风险是真实的，不再只是推断；这张票已把 Flash 磁盘状态改成只看 Platform 卷状态。主机测试 `test_flash_disk_status_does_not_depend_on_calling_task` 与“别的任务格式化并读写 Flash 卷”覆盖，板上证据并入第 2 次上板。ADR 里的“（推断）”可以去掉。
- 2026-11-05 · harness · cite · HAR-11 · 共用 FreeRTOS 桩补了四样：`vTaskDelay`（只让 tick 前进）、`give_from_isr_calls`（`GiveFromISR` 单独计数，用来证明 ISR 回调没有误用任务版 Give）、`freertos_stub_set_give_from_isr_woken`（让 `GiveFromISR` 报告唤醒了更高优先级任务）、`freertos_stub_isr_yield_requests`（`portYIELD_FROM_ISR` 以非零标志被调用的次数）。后者让 `portYIELD_FROM_ISR` 在桩里不再是空宏：凡是编译进主机测试并使用它的源文件，必须同时链接 `freertos_stub.c`（`ui_cell`、`flash_ftl` 已满足，`filesystem_locator` 只取头文件、不用该宏）。桩自测在 `freertos_stub_behavior`，README 已同步。
- 2026-11-05 · harness · cite · HAR-5 · `Tests/flash_ftl` 新增 `filesystem_completion_wait`：真实 Service、SD/Flash 私有执行器、FatFs 与 USER DiskIO 胶水加共用桩，Platform 层用替身（Flash 替身带 RAM 盘）。主机单线程，阻塞钩子在“等待将要发生”时替中断调用已订阅的回调。PASS 证明各分支行为（成功、超时、错误、迟到旧信号被清、创建先于订阅、不依赖调用任务）；不证明真实 ISR 时序与优先级、DMA 与 Cache、迟到 DMA 覆盖 bounce buffer，也不证明 `SDMMC1`/`QUADSPI` 中断优先级满足 `configMAX_SYSCALL_INTERRUPT_PRIORITY`，这些靠第 2 次上板。

# Inbox: ticket-209-sd-abort

- 2026-11-05 · storage · proposed · storage.md 未决问题（迟到的 DMA 完成事件） · 本票（#209，分支 `ticket-209-sd-abort`，基于 `ticket-208-entry-locks`，未上板）已把显式 Abort 落成代码，建议把这条未决问题关闭，改成一句已定事实加待验收：SD 等 DMA 完成超时后，Service 先调 `Platform_SD_AbortTransfer()`（Adapter 自己写有上界的序列，不调 `HAL_SD_Abort`），**硬件先停、信号量后清、下一笔才允许启动**，所以“清理之后、本次 Start 之前才完成”的窗口由顺序关掉，不再靠信号量清理（清理保留作第二道保险）；停住则 Device 回到 READY，可立即再传（不是旧做法的 ERROR），上界内没停住则 `HAL_SD_DeInit`、卷保持 ERROR、拔插卡或显式再 Init 才恢复。仍未证实的是真实硬件上的行为，由 R2.2 板级验收（钩子构建）负责；“超时构造不出来”这个原因不再成立，钩子能制造超时，没有被钩子制造出来的迟到 DMA 也算一条证据。_Why:_ 未决问题的前提（超时后 Device 一定 ERROR，所以窗口难构造）随这张票改变，留着原文会让读者以为超时仍然让卷不可用。
- 2026-11-05 · architecture/storage-seams · proposed · ARC-11 · 建议在“完成等待”规则里补两句：① SD 的完成等待超时一律走显式 Abort，Device 不得带着在飞的 DMA 停在 BUSY 或只被标成 ERROR 而硬件不管；② 顺序是硬件先停、完成信号量后清、下一笔才启动，中止期间落进来的那一次完成留下的信号在中止返回之后清。_Why:_ 中断说不出是哪次传输结束的，信号量清理单独清不到“清理之后、启动之前”的窗口，这是 #207 留给 #209 的；传输序号挡不住旧 DMA 覆盖 bounce buffer（ADR-0024）。代价是 Platform/Component/Adapter 各多一个中止入口，Adapter 越过 HAL 公开函数直接依赖 SDMMC 寄存器（见下一条）。 另外：等待的预算只能来自 Service 自己的有上界常量，FatFs/BSP 传下来的超时一律忽略——CubeMX 生成的 `sd_diskio.c` 传 `SD_TIMEOUT`，等于 HAL 的 `SDMMC_DATATIMEOUT`（0xFFFFFFFF），`pdMS_TO_TICKS` 用 64 位算出约 49.7 天，真卡死时一直持 SD 卷锁、永远走不到 Abort（本票的第一版就漏了这条，因为钩子自带 1 ms 的超时，查不出来）；`filesystem_sd_bsp.c` 改为统一用 `FILESYSTEM_FATFS_BSP_DMA_TIMEOUT_MS`（500 ms），主机测试走真实的 `SD_read` 断言等待是 500 ms。
- 2026-11-05 · architecture/runtime · friction · ARC-8 · Adapter 不再只是“把请求翻译成 HAL 调用”：`sd_stm32_hal_abort_transfer` 为了有上界，绕开 `HAL_SD_Abort`（超时常量 `0xFFFFFFFF` ms），直接写 `SDMMC1` 的 `MASK`/`ICR`/`CMD`/`DCTRL`/`IDMACTRL`，并自己恢复 HAL 句柄的 `State`、`Context`、`ErrorCode`。依赖清单（`State`/`Context` 的写法、`SDMMC_STATIC_FLAGS`、`SdCard.RelCardAdd`、`HAL_SD_RegisterCallback` 要求 READY 等）写在 `Adapters/stm32_hal/sd/README.md`，升级 HAL 时复核。建议 ARC-8 或 Adapters 层说明加一句：“确需越过 HAL 公开函数时，把依赖的 HAL 内部事实列在 Adapter README，升级 HAL 时复核”。 补充：没停住和卡已拔出两条分支不走“让数据通路静止”的序列，`HAL_SD_DeInit` 又不复位 SDMMC 寄存器，IDMA 使能位可能残留，重插后 `HAL_SD_Init` 的 SCR 轮询读会被残留的 IDMA 写进 bounce buffer，所以 Adapter 在 DeInit 之后再做一次 RCC 复位脉冲（`__HAL_RCC_SDMMC1_FORCE_RESET`/`RELEASE_RESET`，SDMMC2 用对应的 SDMMC2 宏，由 `Instance` 选）。它依赖 RCC 复位而不是 HAL，假设复位不需要外设时钟（依据 `HAL_DeInit` 也是不先使能时钟就复位整条总线），没有实测。
- 2026-11-05 · architecture/storage-seams · cite · ARC-21 · 持锁上界：中止发生在持 SD 卷锁时，进持锁上界表的“故障路径”行——500 ms 等待 + 100 ms 中止预算（`SDCARD_ABORT_TIMEOUT_MS`，覆盖 CMD12、DPSM 静止、卡回到 TRANSFER，每一步共用一个截止点）+ 没停住时一次 `HAL_SD_DeInit`，约 0.6 s；一次请求在第一个失败的分块就返回，所以一次调用不超过这个数；小于 T_data（现 2 s）。它不进 R2.1（R2.1 的 20 ms 是正常读）。钩子构建里每次探测给被探测的读多加约 10–15 ms（估计，未测），所以 R2.1 要用钩子关闭的构建量。写方向的预算偏紧（SDHC 写忙最长 250 ms），产品路径不写 SD，超出会走 `STUCK`（重新插卡）。
- 2026-11-05 · architecture/storage-seams · proposed · ARC-11 · 建议补一句拔出事件的规则：Platform 的拔出事件按“最近一次告诉上层的状态”判断（Init 之后、每次成功的 `Platform_SD_Process` 之后记下），不按 Process 入口时 Device 的状态。_Why:_ 读写中途拔卡时，`SDCard_FailTransfer`、`SDCard_AbortTransfer`、被拒的启动会在 Process 之前就把 Device 写成 NOT_PRESENT，旧写法入口状态等于刷新后的状态，拔出事件被吞（ADR-0024 背景里记的问题）：Storage 不卸载卷，被占用的文件槽不释放（拔卡后 `f_close` 因卡不在而失败，不放槽），重新插卡时 `MountSD` 返回 BUSY。#209 第一次让读时拔卡真的走到 Abort 的 NO_MEDIA 分支（见下一条），这条必须随它修，已在 `platform_sd.c` 改掉，Service 接口不变；主机测试 `sd_removal_chain` 覆盖整条链。卷任务票（#195）的“消抖后对账”可以直接建立在这个语义上：插入事件仍按入口状态判断，静默拔出后卡在 Process 之前插回报告一次 INSERTED（Storage 视同换卡）。

- 2026-11-05 · architecture/storage-seams · friction · ARC-21 · 给 #211（卷任务）：CubeMX 生成的 `FATFS/Target/sd_diskio.c` 在 `SD_read`/`SD_write` 成功之后有 `while (BSP_SD_GetCardState() != MSD_OK) {}`，没有超时，而 `BSP_SD_GetCardState` 在 Platform 状态不是 READY 时返回 BUSY。现在只有 Storage Task 一个调用者，状态只在它自己的任务里变，碰不到；但卷任务把卡检测、刷新放到另一个任务之后，如果状态在这个循环里变成非 READY（拔卡、中止停不住进 ERROR），读写的调用者会持 SD 卷锁空转。所以 `Platform_SD_Refresh/Process` 这类会改 Device 状态的入口必须持 SD 卷锁（与 ARC-21 “设备状态由卷锁保护，APP 不绕过” 同一件事），这样状态不会在持锁的读写中途变成非 READY。生成文件不能改，不要靠改它解决。

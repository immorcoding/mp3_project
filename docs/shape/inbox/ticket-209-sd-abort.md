# Inbox: ticket-209-sd-abort

- 2026-11-05 · storage · proposed · storage.md 未决问题（迟到的 DMA 完成事件） · 本票（#209，分支 `ticket-209-sd-abort`，基于 `ticket-208-entry-locks`，未上板）已把显式 Abort 落成代码，建议把这条未决问题关闭，改成一句已定事实加待验收：SD 等 DMA 完成超时后，Service 先调 `Platform_SD_AbortTransfer()`（Adapter 自己写有上界的序列，不调 `HAL_SD_Abort`），**硬件先停、信号量后清、下一笔才允许启动**，所以“清理之后、本次 Start 之前才完成”的窗口由顺序关掉，不再靠信号量清理（清理保留作第二道保险）；停住则 Device 回到 READY，可立即再传（不是旧做法的 ERROR），上界内没停住则 `HAL_SD_DeInit`、卷保持 ERROR、拔插卡或显式再 Init 才恢复。仍未证实的是真实硬件上的行为，由 R2.2 板级验收（钩子构建）负责；“超时构造不出来”这个原因不再成立，钩子能制造超时，没有被钩子制造出来的迟到 DMA 也算一条证据。_Why:_ 未决问题的前提（超时后 Device 一定 ERROR，所以窗口难构造）随这张票改变，留着原文会让读者以为超时仍然让卷不可用。
- 2026-11-05 · architecture/storage-seams · proposed · ARC-11 · 建议在“完成等待”规则里补两句：① SD 的完成等待超时一律走显式 Abort，Device 不得带着在飞的 DMA 停在 BUSY 或只被标成 ERROR 而硬件不管；② 顺序是硬件先停、完成信号量后清、下一笔才启动，中止期间落进来的那一次完成留下的信号在中止返回之后清。_Why:_ 中断说不出是哪次传输结束的，信号量清理单独清不到“清理之后、启动之前”的窗口，这是 #207 留给 #209 的；传输序号挡不住旧 DMA 覆盖 bounce buffer（ADR-0024）。代价是 Platform/Component/Adapter 各多一个中止入口，Adapter 越过 HAL 公开函数直接依赖 SDMMC 寄存器（见下一条）。
- 2026-11-05 · architecture/runtime · friction · ARC-8 · Adapter 不再只是“把请求翻译成 HAL 调用”：`sd_stm32_hal_abort_transfer` 为了有上界，绕开 `HAL_SD_Abort`（超时常量 `0xFFFFFFFF` ms），直接写 `SDMMC1` 的 `MASK`/`ICR`/`CMD`/`DCTRL`/`IDMACTRL`，并自己恢复 HAL 句柄的 `State`、`Context`、`ErrorCode`。依赖清单（`State`/`Context` 的写法、`SDMMC_STATIC_FLAGS`、`SdCard.RelCardAdd`、`HAL_SD_RegisterCallback` 要求 READY 等）写在 `Adapters/stm32_hal/sd/README.md`，升级 HAL 时复核。建议 ARC-8 或 Adapters 层说明加一句：“确需越过 HAL 公开函数时，把依赖的 HAL 内部事实列在 Adapter README，升级 HAL 时复核”。
- 2026-11-05 · architecture/storage-seams · cite · ARC-21 · 持锁上界：中止发生在持 SD 卷锁时，进持锁上界表的“故障路径”行——500 ms 等待 + 100 ms 中止预算（`SDCARD_ABORT_TIMEOUT_MS`，覆盖 CMD12、DPSM 静止、卡回到 TRANSFER，每一步共用一个截止点）+ 没停住时一次 `HAL_SD_DeInit`，约 0.6 s；一次请求在第一个失败的分块就返回，所以一次调用不超过这个数；小于 T_data（现 2 s）。它不进 R2.1（R2.1 的 20 ms 是正常读）。钩子构建里每次探测给被探测的读多加约 10–15 ms（估计，未测），所以 R2.1 要用钩子关闭的构建量。写方向的预算偏紧（SDHC 写忙最长 250 ms），产品路径不写 SD，超出会走 `STUCK`（重新插卡）。
- 2026-11-05 · architecture/storage-seams · friction · ARC-11 · 卡已拔出时 `SDCard_AbortTransfer` 与 `SDCard_FailTransfer` 一样，在 `Platform_SD_Process` 之前就把 Device 写成 NOT_PRESENT，之后 Process 比较前后状态相同，拔出事件被吞（ADR-0024 背景里记的同一个问题）。本票没有改变这一点，也没有加重：超时+拔卡原本就是这个结果。卷任务票的“消抖后对账”要同时覆盖这条路径（`FSABORT no_media` 之后卷必须被卸载）。
- 2026-11-05 · diagnostics/evidence · cite · DIAG-6 · Abort 的结果和耗时（一行 WARN，常开）：`FSABORT <stopped|no_media|stuck|rejected> us=<中止耗时微秒> <R|W> blk=<起始块> n=<块数>`，周期计数器量微秒，计数器没启动时按 tick（毫秒精度）。最长约 44 个字符，放得进 Service Log 的 127 字符。R2.2 用它。
- 2026-11-05 · diagnostics/evidence · proposed · DIAG-7 · 建议补两句落地约定：① “启动日志打印开了哪些钩子”的做法是每个钩子在所属模块首次初始化时投一行 `HOOK <名字> ON <参数>`（WARN，只投一次，标签 `HOOK`），没有 `HOOK` 行就是没开；结果行用各自的标签（迟到 DMA 是 `SDHOOK`）；② 开关是 `filesystem_config.h` 里的宏（默认 `0U`，代码写成 `if (宏 != 0U)`），根 `CMakeLists.txt` 提供同名缓存变量 `MP3_HOOK_<场景>`（迟到 DMA：`MP3_HOOK_SD_LATE_DMA`），Release 打开直接报错。_Why:_ 以后每个钩子都要同样三样东西（开关、启动行、构建保护），写一遍省得每张票重新发明；钩子构建会改变被测路径的时序（迟到 DMA 钩子拉长 SD 持锁），对应的时序行必须在钩子关闭的构建上量，这一点值得进规则。
- 2026-11-05 · diagnostics/logging · cite · DIAG-3 · 日志核算（#209）：Abort 的 `FSABORT` 每次等待超时最多一行，两次之间至少隔一次完整的 500 ms 等待，一张持续超时的卡不会刷屏；钩子构建每 16 次读请求最多多 2 行（`FSABORT` 加 `SDHOOK`，连续播放约十几秒一次）；启动多一行 `HOOK`。`SDHOOK` 行最长约 70 个字符。都在 `Service_Log_Post` 非阻塞的前提下持 SD 卷锁时投递，与 Monitor 5 s 一批的 12 行同时到时占用的消息池不变。

# Inbox: ticket/79-playback-faults

> 以下是 2026-10-17 实施 [#79 播放状态机（二）：坏文件、超时、故障与停止原因](https://github.com/immorcoding/mp3_project/issues/79) 时记下的 Signal，规则正文的改写尚未批准。drain 时提给用户。

- 2026-10-17 · architecture · signal · B5/B6 · BAD_FILE 应答不带曲目数，开机后第一首（或 SELECT 换了代次之后）是坏文件时，状态机的 N 未知，无法环形步进也无法用 N 做上界。本票按 B5“N = 0 走 NO_TRACK”处理：停止 NO_TRACK、重置游标，等于一首坏文件就让“按播放”停下。根因在 Storage：`storage_audio_stream.c` 的 `storage_audio_open()` 在 BAD_FILE 时把 `Generation`、`TrackCount` 清零，而此时它已经解析出曲目（BAD_FILE 只发生在 f_open 与标签探测，曲库窗口早已查到）。建议改 Storage 在 BAD_FILE 时也填 `Generation` 与 `TrackCount`（`AudioBytes` 仍为 0）；状态机已经在这两个字段非零时采用它们（`test_bad_file_record_carrying_track_count_enables_skipping` 固定），Storage 改动合入后无需再动状态机。Storage 是 #75 已合入的公开记录语义，本票没有改。
- 2026-10-17 · architecture · signal · B5 · B5 的“首帧清零”与 B6 的“Start 因参数被拒计入连跳”合起来有一个缺口：被拒的曲目先解出首帧（清零计数）才会在 Start 时被拒，若整库都是不支持的采样率（如 8–24 kHz 的 MPEG-2/2.5，spec 的待核对项），每首的首帧都把计数清零，ALL_BAD 永远不会触发，设备会在库里无限轮转。本票的缓解：首帧与 Start 被拒/R 耗尽出现在同一份 `Pump` 回报里时不清零（真实播放模块在预填完成的那次推进里同时给出两者，所以常见情形覆盖）；两者分在不同推进里时缺口仍在。要彻底关掉，可让 B5 改为“首帧后输出已 Start（或暂停态预填完成）才清零”，需要改 B5 正文，请 drain 时决定。
- 2026-10-17 · architecture · signal · B8 · T_out 的“Platform 运行时”由状态机根据 `Pump` 回报重建：`OutputStarted` 置位，`OutputProgress` 重新计时，`Underruns` 非零（播放模块已 Stop，补满后才再 Start）、暂停、放弃流、流尾放完置零。`ResumeOutput()` 在内部 Start，其报告不外传，所以本票把“恢复成功”直接当作 Start 起算 T_out；若恢复时半区不满、要等下一次 `Pump` 才真正 Start，这段等待会被算进 T_out（至多误报 AUDIO_ERROR 而不是 NO_DATA）。若想精确，可让 `Service_Playback_ResumeOutput()` 的 Start 事实在下一次 `Pump` 回报 `OutputStarted`。板级 T_out 验收（故障注入、2 h 不误触发）仍 `hw:pending`。
- 2026-10-17 · architecture · signal · B6/B10 · 状态机对播放模块 Stop 类失败的判据是 `PauseOutput`/`AbandonStream` 返回 `SERVICE_ERROR`、`BeginStream` 返回 `SERVICE_ERROR` 或 `SERVICE_NOT_READY`，一律归 STOP_FAILED（AUDIO_FAULT 锁存）。`Service_Playback_PauseOutput()` 在 Stop 成功之后 `GetStatus` 失败时也返回 `SERVICE_ERROR`，会被误归为 STOP_FAILED（锁存、重启前不能出声）；`BeginStream` 在“模块未 Init”时返回 `SERVICE_NOT_READY` 也会被如此归类。两者都是编程错误或极罕见，但后果是永久锁存，请 drain 时确认可以接受，或让播放模块用更精确的状态码区分。
- 2026-10-17 · architecture · signal · K3/B10 · “AUDIO_FAULT 锁存后拔卡与代次变化照常处理”在状态机里没有可观察的行为：锁存时已经写过“无流”，没有打开的流，Storage 不会再写 CARD_REMOVED（C12“没有打开的流时不唤醒”）；代次变化只改 Storage 里的代次，游标不跟着变。所以本票没有为它写单独的分支，只有“锁存期间流事实被忽略”的测试。
- 2026-10-17 · architecture · cite · B6 · 流记录里的终止事实（READ_ERROR、CARD_REMOVED）现在不要求开启 OK 已处理：拔卡发生在开启应答之前（C13“消抖结束后卡已拔则以 NOT_READY 或 CARD_REMOVED 收尾”）也能停止。#78 的做法是只在流已开启时认 READ_ERROR，没有测试固定那一点。

- 2026-11-05 · architecture/storage-seams · proposed · ARC-21 · 建议补一句：改 Device 状态的入口（`Platform_SD_Init`、`Platform_SD_Refresh`、`Platform_SD_Process`）必须持 SD 卷锁，APP 不直接调用，一律经 Service 的启动与刷新入口。_Why:_ CubeMX 生成的 `FATFS/Target/sd_diskio.c` 在 `SD_read`/`SD_write` 成功之后有无超时的 `while (BSP_SD_GetCardState() != MSD_OK) {}`，Platform 状态不是 READY 时 `BSP_SD_GetCardState` 返回 BUSY；设备状态在别的任务持锁读写的中途变成非 READY，读写者会持着 SD 卷锁空转。这是 #209 inbox 留给卷任务票的约束，#210 把它写进 `RefreshSD`/`StartSD` 的实现和 Service README；生成文件不能改，所以只能靠互斥。
- 2026-11-05 · architecture/storage-seams · proposed · ARC-21 · 建议补一句：等闸之前调用者不得持任何 Filesystem 锁，违反断言停机（Release 也保留，闸开着时同样检查）。_Why:_ 卷任务要 SD 卷锁才能完成对账并开闸，持锁等闸就是死锁；检查放在等闸之前而不是只靠拿锁时的断言，是因为闸关着时调用者会先睡在闸上，永远走不到拿锁的断言。
- 2026-11-05 · storage/volumes · proposed · STOR-8 · 建议在规则里写明两点：① 闸的等待没有上界，保证开闸的是卷任务——每次暂停之后在所有路径（对账成功、挂载失败、刷新失败、卡一直 ERROR）上都配一次恢复，Service 不设看门狗，也不在超时后放行（放行会让调用者在对账中途挤进去）；`INCLUDE_vTaskSuspend` 为 0，`portMAX_DELAY` 只是约 49.7 天的有限超时，等闸循环在超时后继续等。② “卷没挂”的返回值：按路径或卷操作的入口给 `NOT_READY`，按句柄操作的入口给 `INVALID_HANDLE`（卷没挂则其上所有句柄都已失效，与原行为一致）。_Why:_ ① 写明谁负责，卷任务票的 Check 才有对象；② spec 说“没挂立刻返回 NOT_READY”，但 #195 同时说“失效后 Close 只返回无效句柄”，两处对句柄类入口不一致，实现按后者（保持 Storage Task 现有行为不变），调用者对两者的处理相同（`StatusIsVolumeUnavailable`），所以不影响约定。
- 2026-11-05 · storage/volumes · proposed · STOR-8 · 建议补“拿锁前一次、拿到锁后再确认一次”各自防什么：拿锁前防**白等**（`MountFlash` 持 Flash 卷锁 3.3 至 8.3 s、插卡挂载持 SD 卷锁约 186 ms，调用者没必要陪着等）；拿锁后防**检查与拿锁之间的竞争**（第一次通过后、拿到锁前，卷任务在锁内卸载了卷）。SD 另在等闸之后再看一次，防的是等闸期间的卸载，这样开闸后不去拿锁。挂载标志只由持卷锁的任务写，读一个字节不需要锁，所以拿锁前的读只是提示，拿锁后的读才是依据。

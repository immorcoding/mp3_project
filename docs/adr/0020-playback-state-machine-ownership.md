# ADR-0020：播放状态机归 APP 播放任务，播放模块只管解码与输出

- 状态：已接受。取代 [ADR-0018](0018-playback-advance-ownership.md)。
- 日期：2026-10-08
- 相关 ticket：[0.6.0 真播放重规划](https://github.com/immorcoding/mp3_project/issues/44)、[播放状态机的唯一所有者与代码落点](https://github.com/immorcoding/mp3_project/issues/45)
- 相关决定：[ADR-0002](0002-layering-and-interface-ownership.md)、[ADR-0005](0005-sd-filesystem-task-ownership.md)、[ADR-0017](0017-mp3-decoder-minimp3.md)、[ADR-0019](0019-freertos-static-task-stack.md)

## 背景

ADR-0018 把曲目推进交给 APP 后台任务，但其第 3 条让 Service 播放模块"自行经 Service/filesystem 打开文件"，与 ADR-0005 第 3 条"Storage Task 是 FatFs 唯一的普通任务上下文"冲突。

此外，现有代码中播放游标由 GUI Task 写入（选曲、上一首、下一首），由 Storage Task 重置（重建、作废），两个任务之间没有同步。一旦接上真实播放，播放任务因坏文件跳曲时也要写游标，就会出现三个写者。

## 决定

1. **播放状态机由 APP 播放任务唯一持有。** 曲目推进策略（步进、跳过坏文件、有界停止）、与 Storage 的开启交接和块收发、当前音频流的身份，以及与 GUI 之间的命令、事件、状态三通道，都归播放任务。状态机写成不依赖 FreeRTOS 的纯 C 单元，与任务外壳（等待通知、读写队列）分开，以便主机测试。
2. **播放模块只做解码和输出管线。** Service 播放模块静态持有解码器状态、帧输出和 PCM 半区缓冲。它是 ARC-18 所说的缓冲所有者：Platform 音频只在提交后到完成事件前暂时持有缓冲。管线内部的子状态（预填、静音、排空）由播放模块自己管理。播放模块不认识曲目、序号、文件和存储窗口，只把帧错误、流尾放完、欠载等事实回报给播放任务，由播放任务决定下一步。每帧 scratch 仍是播放任务栈上的局部变量（ADR-0019）。
3. **对外只公开停止、播放、暂停三态。** 三态按用户意图表示：开启和预填期间仍报"播放"。内部阶段（开启中、预填、排空、停止中等）不进入公开合同。停止时附带停止原因。
4. **播放游标只由播放任务写。** GUI 只向播放任务发命令（选曲、上一首、下一首、播放/暂停），当前曲目以播放状态为准。Storage 重建曲库或拔卡时只更新曲库代次，不再写游标；播放任务发现代次变化（开启被拒或流失效）后，自己重置游标并停止。游标仍按 STOR-1 与曲库代次绑定。
5. **文件对象归 Storage Task。** 音频文件的打开、读取和关闭（包括拔卡时）都在 Storage Task 中完成，与 ADR-0005 一致。播放任务只持有流身份，用来识别并丢弃旧流的块；播放模块既不持有文件，也不持有流句柄。
6. **GUI 不碰播放的真值。** GUI 不读文件、不解码、不写游标，也不持有播放状态的真值，只经命令通道输入，经事件和状态通道显示。拖动进度条期间的本地显示属于界面交互，不在本 ADR 范围内。

开启、关闭、取消的协议，以及流身份的具体形式，由[音频流协议：开启、关闭、取消与流身份](https://github.com/immorcoding/mp3_project/issues/48)决定；命令、事件、状态字段与时间口径由[播放后端公开合同](https://github.com/immorcoding/mp3_project/issues/53)决定。两者都在本 ADR 划定的边界之内补充细节，不改变所有权。

## 未采用的方案

- **播放模块持有完整状态机，APP 任务只做外壳。** 播放策略可以集中在 Service 内，但模块要么返回"开第 N 首、还块、写游标"之类的动作让任务执行，要么由 Service 定义一个存储窗口接口交给 APP 实现。两种做法都会引入新概念，还会把曲目推进策略搬进 Service，同时推翻 ADR-0018 第 1 条。APP 中的纯 C 状态机已经可以做主机测试（参照 storage_catalog 的做法），不需要为了可测而把它上移。
- **播放模块自行经 Service/filesystem 打开文件（ADR-0018 第 3 条）。** 与 ADR-0005 冲突，而且拔卡时的关闭顺序会分散到两个任务。
- **对外增加"加载中"状态。** 开启通常只需几十毫秒，用户几乎看不到；增加这个状态会让公开合同多一个状态、GUI 多一种画面。
- **保留 GUI 写游标，或由 Storage 继续重置游标并加临界区保护。** 写者多于一个；坏文件跳曲与用户按键会竞争。临界区也违背了"交接不加锁"的既有做法。
- **撤掉 Storage 中的游标，由播放任务自己记录当前曲目。** 状态少了一份，但要改 STOR 规则、曲库重建路径和窗口高亮，改动面大于只换写者。

## 后果

- ADR-0018 整体废止；其第 1、2 条的意图（推进归 APP、播放模块不持游标）由本 ADR 沿用。
- 实施时，`APP/tasks/gui/music` 中对 `storage_playback_cursor_set/next/previous` 的调用要改为发送命令，GUI 的 playing 标志与假进度改为读取播放状态。`storage_catalog` 中对游标的 init/invalidate 也要移出 Storage Task。STOR-6（高亮核对游标）和 GUI-17（游标更新后才 Apply）要相应修订，已在 shape inbox 中记为 Signal。
- 主机测试从播放任务的纯 C 状态机切入，用假存储窗口和假播放模块驱动；播放模块单独用假的 Platform 音频测试。出声、DMA 与 Cache 只能上板验证。
- 若将来要把推进策略移入 Service，需要新 ADR 取代本决定。
